# 日曆同步功能部署清單

`clasp push` 只上傳程式碼，**不會讓改動生效**。建立新的部署版本是 Apps Script 編輯器裡的手動步驟。

## 前置準備

### 1. 備份現有 `loans` 工作表

在試算表裡對 `loans` 分頁按右鍵 →「複製」，留一份副本。

補欄式 migration 設計上不會動到既有資料，但備份的成本是三秒鐘。

### 2. 日曆分享給 script owner

GAS 永遠以部署者的身分執行，無法「用另一個 Google 帳號」建立事件。所以：

1. 打開目標日曆的「設定和共用」
2. 在「與特定使用者或群組共用」加入**執行這個 GAS 專案的帳號**
3. 權限選「**變更活動**」（不是「查看所有活動詳細資訊」）

事件的建立者會顯示成 script owner 那個帳號，這是這個做法的必然結果。

### 3. 建立 `users` 分頁

新增一個名為 `users` 的分頁：

| A | B |
|---|---|
| `userId` | `displayName` |
| U1234... | 王小明 |
| U5678... | 李小華 |

- 表頭必須**剛好**是 `userId` 與 `displayName`，但兩欄的順序無所謂（程式用欄位名定位）。
- `userId` 可以從 `loans` 分頁的既有紀錄取得。
- 只需要填「常用使用者」。沒登錄的人會顯示他自己的 LINE 暱稱。
- 這個分頁**可以不建**，功能會照常運作，只是所有人都顯示 LINE 暱稱。

### 4. 設定 `CALENDAR_ID`

Apps Script 編輯器 →「專案設定」→「指令碼屬性」→ 新增：

- 屬性：`CALENDAR_ID`
- 值：日曆設定頁面裡的「日曆 ID」（長得像 `xxxxx@group.calendar.google.com`）

**未設定就等於關閉日曆同步功能**，bot 其餘行為完全不變。這也是安全的回滾手段。

## 部署

```bash
clasp push
```

然後在 Apps Script 編輯器裡：

### 5. 重新授權 ← 最容易漏掉的一步

`CalendarApp` 引入了一個**新的 OAuth scope**。web app 是綁著部署當下的授權在跑的，scope 一變而沒有重新授權的話：

> **`doPost` 會整個失敗——不是日曆不同步，是整個 bot 停擺。**

做法：在編輯器裡隨便執行一個函式（例如「執行」下拉選單選 `doGet`），Google 會跳出授權視窗，同意新的日曆權限。

### 6. 建立新的部署版本

「部署」→「管理部署作業」→ 編輯（鉛筆圖示）→ 版本選「新版本」→ 部署。

**`clasp push` 到這一步之前都不算上線。**

## 驗證

依序確認：

1. **`doGet` 回傳 OK** — 用瀏覽器打開 web app URL。失敗代表第 5 步授權沒做成功。
2. **`loans` 多出 `eventId` 欄位（G 欄），既有資料列完全不變** — 這是補欄式 migration 生效的證據。
3. **借一筆器材** — 日曆上出現整天事件，標題為「名字｜器材」。
4. **事件日期範圍正確** — 租 9/11～9/13 的事件應該涵蓋 9/11、9/12、9/13 三天（Google 的整天事件結束日是排他的，程式已經處理，這裡是驗證它有處理對）。
5. **`查器材`** — 回覆顯示 `users` 分頁指定的名稱。
6. **`刪除 <n>`** 一筆未來紀錄 — 日曆事件消失。

```bash
clasp tail-logs   # 觀察第一筆實際借用
```

## 回滾

**清空 Script Properties 的 `CALENDAR_ID` 即可關閉日曆同步**，不需要回滾程式碼、不需要重新部署。

`loans` 的 `eventId` 欄位留著不影響任何既有功能，`users` 分頁也可以直接刪掉。

## 失敗時會發生什麼

日曆同步失敗時：

- **使用者完全無感** — 照常收到「已建立借用紀錄」，日曆是內部細節。
- **借用紀錄仍然成立** — `loans` 是唯一真實來源，日曆只是鏡像。
- **script owner 會收到 Apps Script 的失敗通知信** — 例外會往上拋，這就是通知機制。

所以如果你開始收到 Apps Script 的錯誤信，先看 `CALENDAR_ID` 是不是打錯、日曆分享權限是不是被撤掉了。
